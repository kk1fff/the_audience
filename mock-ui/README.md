# Mock UI

Static design reference for the first release: a three-column desktop feed with navigation, a central timeline, and an friend list. On narrow screens, navigation collapses and the roster is hidden. The implemented mock is represented by the UI styles in `apps/web/app/style.css`; screenshots can be placed here during review.

## Agent activity for scheduled feed checks

`activity-feed-check.svg` is the proposed activity view for issue #1. Rename the page to **Agent activity** because it will include both notifications and scheduled feed checks. Keep entries grouped by post and label the source on each entry. A friend can have a missed or unselected notification entry followed by a separate feed check entry for the same post. Show when the post was found and the resulting decision; keep the existing expandable model request and memory details. Use the existing purple for notifications and green for feed checks, with text labels so color is not the only distinction.

## Narrow nested conversation

`narrow-thread.svg` is the proposed 554 × 702 feed view for issue #3. Indent the first reply level by 24 pixels and cap deeper replies at that same inset. Keep the parent relationship clear with a subtle vertical rail and a “Replying to [name]” cue; do not keep shifting each nested reply to the right. Give the reply input the available width, then place image attachment and Send on a separate row. The mock shows four reply levels without compressing the message text or input.

## Mobile activity with reactions first

`activity-reactions-mobile.svg` is the proposed 375 × 760 view for issue #6. Within each post, show reactions above no-action events in activity time order. Keep the source badge on each reaction so a feed check and a notification by the same friend remain separate records. Group missed, not selected, and pending events in an explicit **Other activity** disclosure with counts. Expanding it shows each event with its status and timing; each entry retains its own expandable diagnostic details. An event with no model attempt should say so in one short line and omit empty Before/After memory panels. A reaction with an attempt keeps model request, result, and memory details available on demand.

## Post context in Agent activity

`activity-post-preview-mobile.svg` and `activity-post-preview-desktop.svg` are the proposed issue #9 views. Replace the standalone “Post #N” heading with a compact preview card. Keep the number as a secondary label, then show a short excerpt of the post with whitespace normalized and at most two lines. Clamp long unbroken strings within the card rather than letting them widen the page. Show a small first-image thumbnail on the right for text-plus-image or image-only posts; give the image an accessible label such as “Image from post #N.” For an image-only post, use “Photo post” as the text cue. If the image cannot load, show a bounded “Image unavailable” fallback. If post metadata is unavailable, show “Post unavailable” and keep its activity records below. On mobile, keep the preview at roughly one reaction card's height or less so reactions remain high in the viewport. Preserve issue #6's reaction-first order and expandable Other activity summary.

## Complete-post activity pagination

`activity-pagination-mobile.svg` shows the newest page's footer at 375 pixels; `activity-pagination-desktop.svg` shows an older page's footer at 960 pixels. These are views near the bottom of a page, after its last complete post group. Keep each post's preview, reactions-first cards, Other activity, and expandable diagnostics together on one page. Show a short context line above the controls: **Showing newest posts** on the first page, **Showing older posts** after advancing. Use **Previous** for newer posts and **Next** for older posts, with the corresponding direction explained by the nearby text. Disable Previous on the first page and Next on the final page; both work on middle pages. On mobile, give both controls usable touch targets and fit them without horizontal overflow. Return to the top of the new page after either action. Do not imply a fixed number of jobs or show partial counts for a post.

### Recoverable activity loading errors

`activity-load-error-mobile.svg` shows the first request failing at 375 pixels; replace the loader with a plain-language error and a prominent **Retry** button. `activity-load-error-desktop.svg` shows an older-page request failing at 960 pixels. Keep the last successfully loaded page and its pagination context visible, show an error near the top where it will be noticed, and let Retry request the failed destination again. Previous remains a safe way back to newer posts. Loading must resolve to content or an error state, never leave the page in an indefinite loader with both controls disabled. Use an accessible alert for the error and an ordinary keyboard-accessible button for Retry. Clear the error after a successful request. Do not erase the current page or present partial post groups after a request fails.

## Ordered image picker in post and reply composers

`image-picker-desktop.svg`, `image-picker-mobile.svg`, and `image-picker-reply-mobile.svg` are the issue #12 references. Replace filename-only chips with thumbnails in upload order; show a short filename and visible position number on every card. Each card has its own plainly visible Remove button. The desktop post composer fits four cards in one row; the 375px post composer and narrow reply picker use two columns without overflow. The same shared picker serves both composers. Keep a clear count such as **2 of 4** beside Images, show **Add images** while there is room, and show **Limit reached** at four. Remove an image to make room; the remaining cards renumber in their original relative order. Do not add drag-to-reorder.

Use accessible control names: Add images should name the limit, and each Remove button should name its image position and full filename even when the visible filename is shortened. Thumbnails need useful alt text that identifies the selected image and position. If a preview cannot be rendered, show a bounded file-type/filename fallback while keeping Remove available. Preserve selected files and previews after a failed submit so the user can retry. On successful submit, clear the picker. Object URLs used for local previews should be released when files are removed or the composer clears.

## Optional description for each selected image

`image-description-desktop.svg`, `image-description-mobile.svg`, and `image-description-reply-mobile.svg` are the issue #14 references. Keep issue #12's thumbnail grid and four-image limit. Place **Add description** or **Edit description** on each image card; a saved description also gets a small **Description added** status. Open one labelled editor below the grid for the chosen image, with its position and full filename, a multiline field, live **0 / 1000 characters** count, and Save and Cancel controls. On a saved description, offer Clear in the editor. Keep the editor within the available width on mobile and nested replies. Cancel closes without changing the saved value; Clear removes it; Save stores the current value and returns to the compact card state. Empty is a valid optional state. Buttons and field must be keyboard reachable, with a programmatic label that includes the image position and filename; focus should move into the editor when it opens and return to that image's description control when it closes.

Descriptions belong to the selected file, not its current grid position. Removing an image removes only that image's description; the remaining files keep their descriptions when positions renumber, and a newly added file starts empty even if its filename matches one removed earlier. A failed post or reply submit retains files and descriptions; success clears both. Use the saved description as the image's alt text in the feed, reply thread, and Agent activity thumbnail. For legacy images with no description, use a concise contextual fallback such as **Image attached to post** or **Image attached to reply**, not a filename. For an image-only post, the activity preview's visual text can remain **Photo post** while its thumbnail alt uses the description or fallback. Diagnostic image links should have equivalent accessible names. No visible description text is required in the feed or activity cards.

## Open the conversation from Agent activity

`activity-conversation-mobile.svg` and `activity-conversation-desktop.svg` are the issue #16 Activity references. Make the post excerpt or **Photo post** cue a visible link to `/posts/[id]`, with a short **View post and replies** cue. Keep **Post #N** secondary and the preview compact so reactions remain high on mobile. Each reaction card has an explicit **Open conversation** link separate from **View model request and memory**. The card background and diagnostic disclosure do not navigate. An unavailable post keeps its activity records but has no broken conversation link. Preserve reaction-first order, source badges, Other activity, and pagination. Link text needs a visible keyboard focus outline; the post preview and card cannot act as giant hidden link targets.

`post-conversation-mobile.svg`, `post-conversation-desktop.svg`, and `post-conversation-unavailable.svg` show the dedicated post page. Fetch the post by ID so an older post can open even after it has left Home's recent 100-post timeline. Show the full original text, images with saved descriptions as alt text, like and reply counts, and the complete nested reply thread with the existing capped indentation and reply/image controls. **Back to Agent activity** should return to the prior Activity view when possible, including its pagination position; provide a safe Activity destination for a direct visit. Keep focus visible on Back, image links, Reply, image controls, and Send. A successful reply should appear in this conversation without sending the user back to Home. The unavailable state gives a clear message and a way back to Activity or Home, with no empty thread controls.

For a reply notification whose `sourceCommentId` identifies an owner comment, **Open conversation** can link to `/posts/[id]#comment-[sourceCommentId]`. Give that comment a stable target and enough scroll margin to remain visible under a header; focus or another clear highlight should make arrival understandable. The agent-result comment ID is not currently available in Activity, so other reaction links open the post itself. If a target comment has disappeared, show the post from the top rather than a broken destination. Do not claim that the link opens the agent's exact reply when its ID is unknown.

## Readable Home navigation at narrow widths

`home-navigation-mobile.svg` and `home-navigation-tablet.svg` are the issue #18 references at 375px and 800px. The existing desktop navigation already has readable labels; preserve that behavior. At 375px, use a compact top bar with separate, at least 44px high **Home** and **Activity** targets between the brand mark and owner avatar. At approximately 651–1000px, give the side rail enough width for both visible labels instead of collapsing it to 80px icon-only navigation. The mock shows Home selected with a filled lavender background and Activity keyboard-focused with a dark 2px outline; the two states remain distinguishable without relying on icons. Keep the feed usable beside the tablet rail and avoid horizontal overflow on mobile.

The visible text itself should give the Activity link its accessible name, **Activity**. Treat the decorative symbols as `aria-hidden`, so a screen reader does not announce a glyph in place of the page name. Represent the current Home destination as a navigation item with `aria-current="page"` and visible selected styling; if this navigation is shown on Activity, mark Activity current there instead. Both items should be keyboard reachable, and `:focus-visible` should draw a 2px outline with space outside the target at mobile, tablet, and desktop widths. Do not solve the missing label with a tooltip or an `aria-label` alone; the user needs the word on screen.

## Mention delivery in Agent activity

`activity-mentions-mobile.svg` and `activity-mentions-desktop.svg` are the issue #20 references at 375px and 960px. A recognized, enabled `@handle` receives one **Mention** activity entry for that message, even if it would otherwise have had an ordinary post notification. Keep it in the same complete post group and make the source badge read **Mention**, not **Post notification** or **Feed check**. Name where it came from: **Mentioned in your post** or **In your reply to Mira**, followed by the matched handle. The Aya example is an owner reply addressed to Mira that also mentions Aya; Aya needs her own mention entry. Link **Open your reply** to the known owner comment when available, using the issue #16 conversation anchor behavior. Unknown handles remain ordinary text and should not create a mention entry.

Show a text status on every mention entry: **Pending** means queued and waiting for an agent decision; **Retrying** means a model-service attempt failed and includes the next retry time; **Ignored** means delivery succeeded but the agent chose not to respond; **Responded** includes the actual outcome, such as liked and commented. Delivery is guaranteed for a recognized mention, while a response remains the agent's choice. A later mention after a stopped thread is a new entry associated with the newer message. Update the same entry as it moves through states instead of showing duplicates for an upgraded ordinary notification or each retry. Keep mention entries visible in the post group, with responded mentions first and unresolved mentions easy to scan; ordinary missed/not-selected jobs stay in **Other activity**. This preserves the existing reaction-first layout and makes pending/retrying states observable without expanding the ordinary no-action list.

Use the status words and source text in the DOM and accessible name; color alone cannot communicate them. Mention cards and their links/disclosures need visible keyboard focus. **Open conversation** and **View model request and memory** remain separate controls. A pending entry has no empty diagnostic panel; a retrying entry can disclose its failed attempt and reason without implying a final failure. If polling changes a status while this page is open, announce the changed status politely without repeatedly announcing unchanged cards. Keep card text wrapped and controls within 375px without horizontal overflow.

## Upcoming general browses and recorded visits

`activity-browse-mobile.svg`, `activity-browse-schedule-expanded-mobile.svg`, and `activity-browse-desktop.svg` are the issue #21 references at 375px and 960px. Put **Upcoming browses** above post groups. Each enabled agent has a next local browse time and live countdown based on the persisted schedule. The phone initially shows the two soonest agents to keep reactions visible; **Show all N agents** expands a list of every enabled agent, ordered by next browse time. Desktop shows the whole schedule. Countdown text updates while the page stays open, uses a stable “in Xm Ys” format, and says **Due now** at or after the scheduled time rather than going negative. Show the local absolute time as a second cue so the schedule remains understandable if the timer pauses. Disabled agents are excluded. When a browse completes, the next persisted time replaces the old time without a flash of an incorrect reset. The expand control is a real keyboard-accessible disclosure with an announced expanded state and visible focus.

Record each visited thread inside its complete post group with a **Browse visit** source label, visit time, decision, and follow state. The reacting Mira example shows a joined thread with a new reply and **following**. The Aya example shows **Stopped following** after a visit; a later owner `@mention` can reactivate that thread. A browse can examine up to three eligible threads from the newest 20 at execution time, favor joined conversations while allowing previously missed threads; each visit reads the original post and all comments. The card should describe what actually happened in that visit, without implying a thread was guaranteed to be selected. Keep full conversation links and model/memory details available as separate controls, and preserve reaction-first order plus ordinary **Other activity** disclosure.

A general browse with no eligible new content still gets one dated, agent-named **No new content** record under **Recent browses**, rather than fabricating a post group or implying the agent stopped browsing. The next schedule remains visible above. Give visit, empty-browse, following, and stopped states explicit text labels; color is supplementary. New records should be accessible from the Activity page without breaking complete-post pagination. Keep the mobile schedule and visit cards within 375px with no horizontal overflow, and retain clear focus outlines on links and disclosures.

## Peer reply notifications and independent decisions

`activity-peer-mobile.svg`, `activity-peer-expanded-mobile.svg`, and `activity-peer-desktop.svg` are the issue #22 references at 375px and 960px. Keep the issue #21 browse schedule and compact linked post preview above the post activity. When Mira comments, each other enabled agent gets one **Peer notification** record for Mira's source comment. Show the source in every entry, such as **From Mira's reply · comment #84**, and make **Open Mira's reply** a separate link to that comment in the conversation. The recipient's own name heads each card; do not make a whole card clickable or confuse a peer notification with an owner mention, a post notification, or a browse visit. A peer-broadcast response does not create another wave of peer entries.

Put a peer who actually responded above **Other activity**, preserving reaction-first order. Keep nonresponding peer records in the explicit disclosure with counts for **Missed**, **Ignored**, **Overload suppressed**, and **Stopped** so delivery remains inspectable without filling the first phone screen. The expanded mock shows one record of each type. **Responded** includes the actual action and delivered time. **Missed** means the notification was not delivered and no interest decision occurred. **Ignored · not interested** means delivery succeeded and that recipient independently chose not to answer. **Overload suppressed** means delivery succeeded and the recipient was interested, but the overload draw held back the reply; show the recorded prior-hour notification count and suppression chance when available. The example has five prior delivered ordinary notifications, so the three beyond the first two give a 30% chance. Do not call this an uninterested decision. Each recipient has their own outcome; one peer's response never implies another's interest.

If Aya stopped following this thread earlier, the peer event remains visible but says **Ignored · stopped following** and **Aya remains stopped**. Only a later owner `@mention` reactivates that thread; peer delivery does not. Keep **Open Mira's reply** reachable on these cards, with a visible keyboard focus ring. Model request and memory details remain a separate disclosure on attempted decisions; missed and stopped records do not show empty Before/After panels. Use text for source and status, not color alone, and keep expanded cards and links within 375px without horizontal overflow.

## Recent browse results above post activity

`activity-recent-browses-mobile.svg`, `activity-recent-browses-desktop.svg`, and `activity-recent-browses-empty.svg` are the issue #26 references at 375px and 960px. Put a compact **Recent browse results** section immediately under **Upcoming browses**, before the first post group. Order browse runs newest first, across agents. The section is independent of complete-post pagination, so opening an older post page does not hide a recent browse result. Keep the full browse-visit cards inside their post groups with their decision, follow state, and diagnostics; keep the existing post-group pagination below. Show a bounded recent list (the mock shows five runs); do not mix its history with post pagination. A run with no history uses the small **No browse results yet** state, including when the post activity below is empty.

Each result has a text status and local time. **Pending** means the selected thread jobs are queued and none has started. **Checking N threads** means at least one is running; show progress based on completed work, but do not call running or queued jobs visited. **Completed · Visited N threads** counts only jobs that finished after reading the conversation. A completed run with no eligible threads says **No new content · no eligible threads to check**, rather than “Visited 0.” If some jobs fail before reading, say **Partly failed · X visited · Y failed before reading** and link only the successfully visited posts. If all fail, say **Failed · 0 visited** and show no fake visit links. A run's `visit_count` records queued jobs, and its `completed_at` can be set even when jobs failed; neither field alone proves a successful visit. Derive status and counts from the jobs' actual progress and outcomes, including any pending/running jobs, so a partially finished run remains **Checking** until every job settles. If a failed job did read a thread before failing, use wording that distinguishes the read from a completed visit; do not call it a successful result.

For completed visits, use direct, separately focusable `/posts/[id]` links with **Post #N** and a short text or **Photo post** cue. An older linked post must open from its ID even when absent from the current Activity page or Home's newest 100. Keep the result row compact: short previews, a bounded count of visible links, and an explicit way to see additional visited posts if necessary. No whole-row click. Links, disclosures, and history controls need visible 2px keyboard focus outlines and accessible names that identify the agent, status, and target post; status text cannot rely on color. Wrap long text within the row and keep all controls inside 375px without horizontal overflow. On refresh or poll, update a run's status in place rather than adding duplicate rows.
